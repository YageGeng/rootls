# 剪贴板历史插件设计

2026-11-17 · 用户已确认设计

## 一次复制，一条历史

rtools 运行期间，用户可以开启或关闭剪贴板记录。用户已确认图片需要保留独立副本，原文件删除后仍能复制，并且一次复制可能包含多张图片。历史以一次系统复制为单位，保存其中每个成员及系统给出的顺序。

例如，在文件管理器中一起复制「前景.png」「说明.pdf」「背景.jpg」，历史出现一条“2 张图片，1 个文件”。两张图片各有自己的完整内容，PDF 只保存路径。搜索“背景”能找到整条记录。即使两张原图都已删除，仍能从这条记录取回两张图片。

| 复制的内容 | 保存与恢复 |
| --- | --- |
| 文本 | 保存原文，按纯文本复制回去。 |
| 截图、编辑器里的“复制图片” | 保存系统给出的图片内容。只有像素数据时编码为 PNG，保留透明度。 |
| 一张或多张图片文件 | 逐个读取本次复制给出的图片文件，保存内容、格式、名称和来源路径。PNG、JPG、JPEG 纳入首版验收。单张可作为图片粘贴，多张可整组粘贴。 |
| 图片与其他文件混选 | 保留各自的位置。图片保存副本，其他文件和文件夹只记路径。 |
| 只有普通文件或文件夹 | 保存有序路径列表，支持按文件名或目录查找，选择“复制路径”可一次取回全部路径。 |

先检查系统的保密标记，再枚举文件列表或系统在本次复制里提供的全部原生图片成员。同一成员同时提供 PNG 和 TIFF 时只取一份图像。两个独立成员即使字节相同也保留两个位置。分组以系统复制事件为准，短时间内先后复制的内容仍各自成条。普通文本中的路径作为文本处理，文件访问仅限来源应用明确提供的文件引用。

## 后台记录与开关

设置页增加“记录剪贴板历史”，首次安装默认关闭，开关保存在 `settings.toml` 的 `[clipboard]` 表中。设置加载后，由主进程持有一个记录器。启动器和分离窗口共享历史，窗口隐藏、关闭或从未打开均不影响已启用的记录。重新启动时沿用保存的开关。[应用入口](../../../crates/rtools/src/main.rs) · [设置存储](../../../crates/rtools/src/settings/mod.rs)

开启和恢复监听时，从此后的新复制开始。关闭立即停录并使在途采集失效，旧记录仍可查询。清空时使旧监听和排队的写入失效，并重新订阅。macOS 和 Windows 用清空瞬间的系统变更序号衔接前后两次订阅。停录时，已经进入 SQLite 等待提交的旧记录也会回滚。历史回写到系统剪贴板时，只抑制这次由 rtools 发起的回写，紧随其后的真实复制照常处理。

macOS 可通过 `NSPasteboard.changeCount` 检测变动，逐个读取 `pasteboardItems`。Windows 订阅 `WM_CLIPBOARDUPDATE`。X11 监听 `CLIPBOARD` 的所有者变化，Wayland 通过 data-control 订阅普通剪贴板的变化。这样连续复制两张格式相同的截图也能产生两次采集机会。设置页区分已关闭、正在记录和监听不可用。macOS 的轮询可能错过两次检查之间已被覆盖的内容。[Maccy 监听实现](https://github.com/p0deje/Maccy/blob/master/Maccy/Clipboard.swift) · [Windows 通知](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-addclipboardformatlistener) · [Wayland 监听](https://docs.rs/wl-clipboard-rs/latest/wl_clipboard_rs/)

## SQLite 存储与搜索

采用本地 SQLite 保存历史和图片。另一种可行方案是像 Klipper 那样把载荷放在文件系统，在数据库中保存索引。首版建议将原始字节放进库里，一次事务即可提交整组，淘汰或删除整组也有明确的边界。接收程序需要文件路径时再按需导出。[Ditto 的数据库结构](https://github.com/sabrogden/Ditto/blob/master/src/DatabaseUtilities.cpp) · [Klipper 的历史存储](https://github.com/KDE/plasma-workspace/blob/master/klipper/historymodel.cpp)

| 数据 | 用途 |
| --- | --- |
| 历史记录 | 稳定 ID、最近复制时间、整组指纹。列表按首次创建顺序倒序显示。重复复制刷新保留顺序，列表位置保持稳定。 |
| 有序成员 | 以记录 ID 和组内序号为键。按类型保存文本、原始文件名与路径或图片格式、完整字节。图片读取失败时保留位置、已知路径和失败状态。 |

文本、文件名和路径支持参数化子串搜索。命中任一成员就返回整组，一组仅显示一次。图片可按类型浏览，检索其文件名。列表查询只取摘要，完整图片在复制或打开预览时读取。

对整组按成员类型、可恢复内容、来源路径和顺序判断重复。相同的一组再次复制时更新最近时间。交换两张图片的顺序会形成不同的历史。采集时及时取得文件或数据句柄，图片读取、校验和数据库写入在后台完成。单张原图已消失、无权读取或损坏时，其余成功的成员仍在同一事务提交，界面标明未保存的图片数。

建议首版保留最近 1,000 次复制，并对已保存内容使用 512 MiB 的总预算，超过任一限额从最旧的完整记录开始淘汰。单次复制本身超出总预算时，提示原因并保留已有历史。日志记录启停、失败原因和数量，省略正文、图片内容和完整路径。

## 搜索、预览和重新复制

在启动器搜索“剪贴板”“剪切板”或 `clipboard` 进入插件，输入关键词筛选，方向键选择历史，回车执行该条目的复制操作。历史使用单列，每行右侧提供复制和删除。含图片的记录同时提供预览按钮。多张图片在同一行显示数量，打开后在单独的预览页按原顺序逐张查看。左右方向键切换图片，Esc 返回原来的筛选和滚动位置。默认动作是“复制整组”，选中某一张也可以单独“复制图片”，供仅支持粘贴单幅位图的应用使用。单条删除与清空作用于历史副本。

复制单张图片直接从 SQLite 读取图片字节。整组含多张图片，或同时含图片和文件时，将图片从库中写到 rtools 私有目录，保留可读文件名，每个成员使用独立目录以容纳同名文件。普通文件沿用原路径。准备好后，按原顺序一次性发布文件列表，让支持多文件粘贴的应用收到全部成员。

| 平台 | 整组写回 |
| --- | --- |
| macOS | 调用 `NSPasteboard.writeObjects`，一次传入有序的文件 URL 数组。项目锁定的 GPUI macOS 后端支持单图写入，多成员写入走文本分支，因此整组采用原生接口。[AppKit 写入接口](https://developer.apple.com/documentation/appkit/nspasteboard/writeobjects%28_%3A%29) |
| Windows | 使用一个 `CF_HDROP`，其中按顺序放置各成员的完整路径。[Windows Shell 文件列表](https://learn.microsoft.com/en-us/windows/win32/shell/clipboard#cf_hdrop) |
| Linux | 使用一个 `text/uri-list`，每个成员一个正确转义的文件 URI。Wayland 上保持数据源可供接收方读取。[URI 列表格式](https://www.iana.org/assignments/media-types/text/uri-list) |

仍被当前剪贴板引用的导出文件需要跨窗口关闭和进程重启保留。在确认剪贴板已替换后清理旧导出。显式清空时同时清理插件生成的副本，若当前剪贴板引用这些副本，在确认框标明影响。始终只清理插件自己的目录。组里若有已失效的普通文件路径或采集失败的图片，标明缺少的成员，提供“复制可用的 N 项”和复制原路径的操作。准备导出失败时保留原有剪贴板。

## 验收

1. 记录开启、启动器隐藏时连续复制不同内容，重启后能搜到。关闭开关或清空历史时正在读取的大图不会在稍后写入。
2. 一次复制来自不同目录的多张图片，其中两张同名、内容不同。确认只有一条历史，出现顺序和数量正确，搜索第二张文件名也命中该组。
3. 删除或移动测试原图，重启 rtools。单张粘贴仍得到原图；整组粘贴到支持多附件的应用时，核对每个成员的顺序和完整内容。
4. 混选两张图片和一个 PDF。PDF 只记路径，一张图读取失败或 PDF 后续被移走时，界面标出具体成员，另一张图仍可恢复。
5. 一张截图同时提供 PNG 和 TIFF 表示时只出现一张。连续两次复制不同的 PNG 截图时出现两条。回写整组后立刻手动复制的新内容也能入库。
6. 用保密标记、整组超限和数据库写入失败的输入检查状态与历史完整性。分别在 macOS、Windows、KDE Wayland 和 X11 验证系统监听及目标应用粘贴。

### 已做的技术验证

设计阶段在 macOS 上用临时 SQLite 库保存 PNG、PDF 路径和 JPEG。删除两张原图并重开数据库后，按第二张图的中文名找到了整组。将导出的图片和原 PDF 路径按顺序写入独立命名剪贴板，写入进程退出后，另一个 AppKit 进程读回了三个文件 URL 及其内容。

实现后，用插件实际的原生监听、SQLite 存储及写回代码复验了后台多图采集、删除原图后的整组及单张恢复、保密标记、连续同格式截图和停录。GPUI 离屏窗口用包含两张图片的测试记录验证了预览、搜索和取消清空。独立 macOS 剪贴板验证了清空前未轮询的复制和重新订阅期间的新复制。Xvfb 虚拟 X 服务器验证了同一窗口复用时间戳时的连续通知，旧传输被丢弃，新通知仍可处理。Windows 和 Linux 后端通过对应目标的 Rust 编译与 Clippy 检查，实际桌面的文件管理器和聊天应用粘贴仍待实机验收。

单条删除的回归测试覆盖了删除前已经开始的重复采集、排队中的其他内容和删除后再次主动复制。两张图片均未保存时，离屏窗口仍提供“复制原路径”，存储测试核对了两条路径的顺序。Xvfb 上的独立接收程序逐字节读回 23.7 MiB 的 4K PNG，随后也读到了新复制的文字。四次启停均释放了请求窗口。带旋转标记的 JPEG 转为 PNG 后保留了显示方向。Windows 监听循环用模拟系统事件验证了剪贴板解锁、新复制替换旧内容，以及等待期间停录。
